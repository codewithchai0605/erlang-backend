# 0009 - Platform-friendly configuration and database TLS
Status: accepted
Context: The backend must run unchanged on a developer laptop, in Docker Compose and on Render with a managed PostgreSQL such as Neon. Render injects `PORT`; managed providers hand out one connection URL and require TLS (Neon also routes connections by SNI and offers a PgBouncer-style pooled endpoint).
Decision: `chat_config` (pure, unit-tested) understands `PORT` (fallback for `CHAT_HTTP_PORT`) and `CHAT_DATABASE_URL`/`DATABASE_URL` (expanded into `CHAT_DB_*`, with libpq `sslmode` mapped to `CHAT_DB_SSL=disable|require|verify`). Explicit `CHAT_*` variables win; empty values count as unset. `chat_pg_worker` always sends SNI and supports `require` (encrypted, unverified) and `verify` (OS trust store + host name). Migrations take a transaction-scoped advisory lock per step instead of one session-level lock. The default bind address is back to `127.0.0.1` and the Docker image sets `0.0.0.0` itself.
Consequences: no shell parsing of URLs in entrypoints; the same logic runs natively and in containers; a bad URL is reported by variable name only (it contains a password). Cost: only the common URL shape is supported. `require` does not authenticate the server; `verify` is recommended once it works with your provider. The transaction-scoped lock is safe through transaction pooling, which a session-level `pg_advisory_lock` is not.
