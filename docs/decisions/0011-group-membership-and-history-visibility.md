# 0011 - Group membership, roles and history visibility
Status: accepted
Context: The schema already had `kind = 'group'` and `role`. Rules were needed for who may change a group and what new members may read.
Decision: Roles in use: `owner` (creator) and `member` (`admin` is reserved). Only the owner adds, removes and renames; anyone may leave; the longest-standing member inherits ownership; an empty group is deleted. Direct chats cannot be modified. New members see only messages after they joined: `conversation_members.history_from_seq` is set to the conversation's `last_seq` while the conversation row is locked (`SELECT ... FOR UPDATE`, the same lock message inserts take), and their receipt marks start there too (no phantom unread). The server enforces the boundary in sync and history; clients only adapt (a conversation with no visible history is "synced up to last_seq"). Membership is always read from the database, never cached for messages.
Consequences: simple, defensible privacy semantics (as in most messengers); no per-message ACL table; membership changes serialise with sends in that conversation. Cost: removed members' old messages are shown as "Former member" because their names are no longer in the member list; no system messages ("X was added") in the timeline yet; admins and "everyone can add" policies are future work.
