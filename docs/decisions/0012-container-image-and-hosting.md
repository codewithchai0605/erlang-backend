# 0012 - Container image, Compose and Render
Status: accepted
Context: Running Erlang, rebar3 and PostgreSQL natively on Windows is hard; hosting on Render should need no special steps.
Decision: One multi-stage `Dockerfile` at the repository root (the build needs `../proto`). Build stage `erlang:N` (rebar3, compilers), runtime `erlang:N-slim` from the same Debian release (a release links OpenSSL/ncurses dynamically). Dependencies are fetched in a separate cached layer. The release runs as a non-root user from a read-only directory (`RELX_OUT_FILE_PATH=/tmp`), under `tini`, with epmd/distribution on loopback, `-name chat@127.0.0.1`, crash dumps off, and a CRLF-stripped entrypoint that generates a random cookie when none is given. `docker-compose.yml` starts PostgreSQL and the backend and always uses its own database; `render.yaml` is a Blueprint for a Docker web service expecting an external database URL. `.dockerignore` keeps `.env` out of images.
Consequences: `docker compose up --build` is the whole local setup; the same image runs on Render. Cost: the image contains Erlang twice (bundled ERTS plus the base image), several hundred MB (not measured); acceptable for clarity. The Dockerfile is lint-clean and its steps were run natively, but `docker build` was not executed in the authoring environment. The single-node design means Render must run exactly one instance.
